# RemoteHand Notes v0.1.0 Design Specification

Status: **Approved design baseline**

This document records the agreed product and interaction design for the first RemoteHand Notes release. It is a design checkpoint, not an implementation claim.

## 1. Product identity

RemoteHand Notes is a private-by-design notes plugin for RemoteHand.

Its primary UX is a board of digital sticky-note cards, closer to a lightweight sticky-note/Keep-style experience than a traditional document editor.

The plugin supports two first-class note types:

- Plain note
- Checklist note

The Notes plugin is intentionally distinct from the RemoteHand Editor plugin.

## 2. Privacy and Vault storage

All user-authored note content and private note metadata are encrypted through RemoteHand Vault.

This includes, at minimum:

- Title
- Body
- Checklist items and completion state
- Labels/tags
- Color
- Pin state
- Archive state
- Lock state
- User-authored attachment metadata
- Manual ordering metadata where practical
- Other private note metadata unless a minimal structural locator must remain outside encrypted content

The plugin should reveal as little structural information as practical outside encrypted content.

Notes does not implement its own encryption system.

RemoteHand core owns:

- Vault cryptography
- Vault create/unlock/lock state
- Passphrase handling
- Key handling
- Permission enforcement
- Namespace enforcement

Notes must use its own scoped Vault namespace, expected to be under a namespace such as:

`plugin:remotehand.notes/...`

The plugin must not receive the Vault passphrase, master key, or derived Vault key.

When Vault is locked, Notes must not expose note titles, snippets, labels, attachments, or other decrypted note content. The board should show a locked-state UI with an action to request host-owned Vault access.

## 3. Board and card layout

The main Notes view is a sticky-note card board.

### Layout

- Responsive masonry/grid layout
- Cards use a consistent width within the current layout
- Card height grows naturally with content
- Long content is preview-clamped so one note does not dominate the board
- Very narrow panels fall back to a single column
- No manual per-card resizing in v0.1.0

### Card contents

A card may show:

- Title
- Short rendered Markdown preview
- First few checklist items
- Image thumbnail when appropriate
- Compact attachment indicators
- Labels/tags
- Pin state
- Color
- Subtle updated-time information if useful

Actions should remain visually lightweight and may appear on hover/focus where appropriate.

### Pinned notes

Pinned notes appear in a separate **Pinned** section above ordinary notes.

Pinned and unpinned notes have separate ordering groups.

## 4. Card ordering and rearranging

Users may rearrange cards by drag-and-drop.

Ordering behavior:

- Default automatic order: most recently updated first
- Once the user manually rearranges cards, manual order is preserved
- Pinned cards can be reordered within the Pinned section
- Regular cards can be reordered within the regular board
- Dragging within an ordering group must not implicitly change pin state
- Manual ordering persists across restarts
- Archive maintains its own ordering state
- Responsive column changes preserve logical card order

The board exposes sort modes:

- Manual
- Updated
- Created
- Title

Switching to an automatic sort must not destroy the saved manual order. Returning to Manual restores the previous manual arrangement.

## 5. Plain notes and lightweight Markdown

Plain notes support lightweight Markdown.

### Editing model

- When not actively editing, Markdown is rendered
- Clicking/focusing the body switches to editable Markdown source
- No split-pane preview
- No separate Save button
- Autosave handles normal persistence

### Supported Markdown subset

v0.1.0 should support common lightweight constructs:

- Headings
- Bold
- Italic
- Strikethrough
- Bulleted lists
- Numbered lists
- Links
- Inline code
- Fenced code blocks
- Blockquotes

Out of scope for v0.1.0:

- Tables
- Footnotes
- Embedded HTML
- Math
- Extension/plugin syntax

Checklist notes remain a real structured note type rather than Markdown `- [ ]` syntax.

## 6. Checklist behavior

Checklist notes are first-class structured notes.

Behavior:

- Enter on an item creates the next item
- Enter on an empty item ends checklist entry
- Items can be reordered by drag-and-drop
- Checking an item moves it to a Completed section at the bottom
- Completed items remain visible by default
- User can hide/show completed items
- Unchecking a completed item moves it back to active items
- Card preview shows only the first few items and may show `+N more`
- Completed items are visually subdued
- Plain note <-> checklist conversion is allowed when the conversion is predictable

Out of scope for v0.1.0:

- Nested checklist items/subtasks

## 7. Autosave

Normal editing is autosaved.

Default behavior:

- Short idle/debounce delay, approximately 500-800 ms
- No normal Save button required
- Autosave applies to plain notes and checklist notes

The exact default may be exposed in Notes Settings.

## 8. Labels and organization

v0.1.0 uses labels/tags only.

There are no folders.

Behavior:

- A note may have multiple labels
- Labels appear as chips on cards
- Clicking a label filters the board
- Search includes labels
- Archived and trashed notes retain their labels
- Labels are Vault-encrypted because they are user-authored metadata

## 9. Search

Global search covers:

- Active notes
- Archived notes

Normal/global search excludes Trash.

When the user is inside Trash, search applies to Trash.

Search should include relevant private fields such as:

- Title
- Body text
- Checklist item text
- Labels/tags

Locked notes in the edit-protection sense remain searchable because their content is not hidden; this is separate from Vault being locked.

## 10. Archive

Archived notes leave the main board and appear in a dedicated Archive view.

Rules:

- Label filters work in Archive
- Search covers archived notes from global search
- Pin state is preserved internally while archived
- Restoring/unarchiving a note returns it to Main and restores its pin state

## 11. Trash and deletion

Deleting a normal unlocked note moves it to Trash.

Trash behavior:

- Trash has its own view
- Notes may be restored from Trash
- Permanent deletion is only available from Trash
- Permanent deletion should require confirmation
- Empty Trash deletes eligible unlocked trashed notes
- Locked trashed notes are skipped by Empty Trash
- Empty Trash should report how many notes were deleted and how many locked notes were retained

Permanent deletion removes the note and its encrypted attachment blobs.

## 12. Note lock

The Notes **Lock** feature is edit/destruction protection, not privacy hiding and not a second password.

A locked note/checklist remains visible and readable.

### Allowed while locked

- Open/view
- Render Markdown
- View checklist state
- Open/view attachments
- Search/filter
- Board rearranging
- Restore from Archive to Main
- Restore from Trash to Main

### Blocked while locked

- Edit title
- Edit body
- Add/remove/reorder checklist items
- Change checklist completion state
- Add/remove/reorder attachments
- Change labels
- Change color
- Change note type
- Change other note-owned content/state
- Archive from Main
- Move to Trash
- Permanent delete

### Archive-specific behavior

A locked archived note:

- Remains read-only
- Cannot move to Trash
- Cannot be permanently deleted
- May be restored/unarchived to Main

### Trash-specific behavior

A locked trashed note:

- Cannot be permanently deleted
- Is skipped by Empty Trash
- May be restored to Main

The simple mental model is:

**Lock protects a note from modification and destruction, but never prevents recovery back to Main.**

Unlocking a note is an explicit simple action and does not require a password.

## 13. Colors

Notes can use sticky-note-style colors.

Color is part of the note's private metadata and is Vault-backed.

A small predefined palette is sufficient for v0.1.0 unless implementation work gives a strong reason to add custom colors.

## 14. Attachments

Both plain notes and checklist notes support:

- Image attachments
- General file attachments

Attachments live in a **separate attachment area**. They are not embedded inline in Markdown.

### Image behavior

- Images can show thumbnails on cards when appropriate
- Clicking an image opens a larger preview
- Clipboard-pasted images may be attached directly
- Drag-and-drop images onto an open note should be supported

### File behavior

- Regular files display as compact chips/rows
- Show useful metadata such as filename, type, and size
- Clicking a file opens it with the system default application
- Drag-and-drop files onto an open note should be supported

### Attachment ordering

- Attachments can be reordered while the note is unlocked
- Locked notes may open attachments but may not add/remove/reorder them

### Card previews

Cards show only a limited attachment preview and may display `+N more` for additional attachments.

### Archive/Trash

- Archive preserves attachments
- Trash preserves attachments
- Permanent deletion deletes the note's encrypted attachment blobs

## 15. Attachment storage direction

Attachment payloads should be Vault-protected too.

Preferred architecture:

- Note document stores encrypted note data plus references to attachment blobs
- Attachment payloads are separate encrypted blobs
- Large binary payloads should not be embedded directly into the ordinary note document

This avoids rewriting large binary payloads whenever a small note edit is autosaved.

The current RemoteHand Vault document API has a bounded document size, so implementation must review whether Notes requires a dedicated larger encrypted binary/blob capability in RemoteHand core.

This is an architectural review item before attachment implementation, not permission to store plaintext attachment sidecars.

## 16. Attachment limits and defaults

Notes Settings provides configurable limits.

Suggested initial defaults:

- Maximum file attachment size: 10 MiB
- Maximum image attachment size: 8 MiB
- Maximum total attachment size per note: 50 MiB
- Maximum attachment count per note: 10
- Image resizing/compression: enabled by default

These are defaults, not product-level ceilings.

The user may raise or lower them.

Notes should not impose arbitrary code-level maximums merely to enforce product policy. Only unavoidable technical constraints in the underlying Vault/storage/API should constrain values.

## 17. Expanded note editor

Clicking a card opens a larger centered modal/overlay.

Behavior:

- Board remains visible but dimmed behind the editor
- Large but not full-screen
- Internal scrolling for long content
- Title at top
- Body/checklist in main area
- Separate attachment area below
- Labels, color, pin, archive, and lock controls available in the editor UI
- Autosave remains active
- Closing returns to the previous board position
- Esc closes the editor
- Clicking outside may close when no transient UI is open
- No Save button
- Locked notes open in the same editor in read-only form with Unlock available

## 18. Notes Settings

Notes owns a plugin-specific Settings UI, opened from a gear/settings control in the Notes top bar.

### Attachments

- Maximum file size
- Maximum image size
- Maximum total attachment size per note
- Maximum attachment count per note
- Image resize/compression toggle
- Image compression/quality preference as appropriate

### Editing

- Autosave delay
- Markdown render/edit behavior if exposing it proves useful

### Board

- Default sort mode
- Default card density/size
- Default completed-checklist visibility

### Behavior

- Confirm before permanent delete
- Confirm before Empty Trash

Vault security policy remains owned by RemoteHand core and does not belong in Notes Settings.

## 19. Keyboard shortcuts

Initial shortcuts:

- Ctrl+N — new note
- Ctrl+Shift+N — new checklist
- Ctrl+F — focus Notes search
- Esc — close expanded note editor / dismiss transient UI
- Ctrl+L — lock/unlock current note
- Ctrl+P — pin/unpin current note
- Ctrl+Shift+A — archive current note
- Delete — move current note to Trash, only when unlocked
- Ctrl+Z — undo while editing
- Ctrl+Y — redo while editing

Notes should not claim RemoteHand-owned function keys unless core/plugin behavior is explicitly extended later.

## 20. Reminders

Reminders are deliberately deferred beyond v0.1.0.

## 21. Out of scope for v0.1.0

Unless revisited explicitly:

- Folders
- Nested checklist items
- Full Markdown/document-editor feature set
- Markdown tables/footnotes/math/HTML
- Inline body attachments
- Reminder system
- Separate note passwords/PINs
- Hidden-note privacy mode separate from Vault
- Manual per-card resizing
- Full version history/recovery UI
- Multi-window note editing

## 22. Core integration review before implementation

Before implementing the full plugin, inspect the current RemoteHand v1.3.0 Vault/plugin API and confirm:

1. Canonical Notes plugin ID and scoped Vault namespace
2. Required Vault document permissions
3. Host-owned Vault access-request flow
4. Locked-Vault UX from a real plugin
5. Whether current Vault document APIs are sufficient for note documents
6. Whether a dedicated Vault encrypted-blob capability is needed for attachments
7. Atomicity/consistency model between note metadata and attachment references
8. Cleanup behavior for orphaned attachment blobs
9. Plugin storage usage for non-private preferences only, if needed

Any required RemoteHand core change should be minimal, generic, and reusable by future plugins rather than Notes-specific where practical.

## 23. Implementation principle

Build the smallest clean foundation that satisfies this specification.

Do not silently expand Notes into a document editor, task manager, file manager, or independent cryptographic subsystem.

The defining experience is:

**private Vault-backed sticky notes and checklists that are fast to capture, easy to arrange, safe from accidental edits/deletion, and simple to organize.**
